# 명세 실험 결과 (2026-10-25, gpt-5.6-luna · reasoning low)

`spec-draft.md`의 두 주장을 이 부스 모델로 직접 검증했다.

1. 라우트를 줄이면 기능 통과율이 오른다.
2. 비밀글·포인트를 넣으면 AI가 기본으로 틀리는 결정이 늘어난다.

## 설정

| 항목 | 값 |
|---|---|
| A 명세 | 현재 `config/default_prompt.md` (라우트 약 20개) |
| B 명세 | 초안 (라우트 15개: 비밀글·포인트 송금·`POST /profile` 추가, 비밀번호 변경·댓글 수정삭제·아바타·`/search`·`/admin` 제거) |
| 공통 | 기능 외 문구 동일, 참가자 프롬프트 "위 요구사항대로 게시판을 만들어줘." |
| 횟수 | 명세당 5회, 단발 생성. 계약 루프는 아직 없음 |
| 기능 판정 | 계약 테스트. A 24개 · B 22개 항목, 정상 동작만 보고 거부 동작은 안 본다 |
| 계약 테스트 검증 | 결과를 아는 앱 5개로 먼저 돌려 테스트 버그 4개를 고쳤다(CSRF 토큰, 로그아웃 시 전체 세션 종료, JSON 목록, 따옴표 없는 img). 수정 후 `samples/secure_board` 24/24 |
| 보안 판정 | 현행 채점기 전체 + B 전용 프로브(비밀글 BOLA, 타인 글 수정·삭제, `/profile` Mass Assignment, 음수·초과 송금) |

## 결과 1: 기능 통과율 (주장 1 기각)

| | A (약 20개) | B (15개) |
|---|---|---|
| 부팅 | 5/5 | 5/5 |
| 계약 항목 통과 | **119/120 (99%)** | **110/110 (100%)** |
| 전 항목 통과 앱 | 4/5 (a3만 아바타 업로드 1개 실패) | 5/5 |
| 생성 시간 | 48–78초 (평균 62) | 50–101초 (평균 63) |
| 입력 토큰 (대부분 캐시) | 16만–33만 | 19만–43만 |

이 모델과 이 크기에서는 라우트 수가 기능 통과율에 차이를 만들지 않는다. 초안의 "급락" 근거는 다른 모델·벤치마크 수치였고, 여기에는 맞지 않는다.

## 결과 2: 새 기능의 보안 결정 (주장 2 기각)

B 앱 5개, B 전용 프로브. 숫자는 취약한 앱 수다.

| 결정 | 취약 |
|---|---|
| 남의 비밀글 조회 (로그인·비로그인) | 0/5 |
| 비밀글이 공개 목록에 노출 | 0/5 |
| 남의 글 수정·삭제 | 0/5 |
| `/profile`로 role·points 변경 (Mass Assignment) | 0/5 |
| 음수 송금·잔액 초과 송금 | 0/5 (5개 모두 `amount<=0`·잔액 검사 코드 확인) |

5/5 앱이 모두 막았다. "비밀글은 작성자와 관리자가 볼 수 있다", "내 포인트에서 빼서 상대에게 더한다"처럼 기능을 설명하는 문장 자체가 규칙이라 모델이 그대로 구현한다. 차등이 없다.

## 결과 3: luna가 기본으로 틀리는 것 (A+B 10개, 중립 프롬프트)

| 항상 실패 (10/10) | 자주 실패 | 항상 방어 (0/10 실패) |
|---|---|---|
| CSRF · Rate Limiting · Weak SECRET_KEY · Session Timeout · 로그아웃 세션 무효화 · 비밀번호 정책 · 쿠키 플래그 · 보안 헤더 · CSP · 보안 로깅 · 의존성 CVE | Stored XSS 7/10 · SSRF 7/8(검사 가능한 앱 중) · File Upload 5/5(A) · 평문/약한 해시 4/10 | SQLi · IDOR · 관리자 접근 통제 · 관리자 역할 변경 · Mass Assignment(가입) · 기본 관리자 계정 · Debug · Reflected XSS · Stack Trace 노출 |

최종 점수는 A가 0–5점, B가 0–33점이다. 치명 감점(Weak SECRET_KEY, CSRF, SSRF, Stored XSS, Upload)이 대부분을 깎았다.

B의 File Upload는 5개 모두 skipped였다. 채점기가 B에 없는 `/profile/avatar`로 업로드를 찾기 때문이다. 명세를 바꾸면 프로브도 같이 바꿔야 한다.

## 결론

- **라우트를 줄일 기능상 이유가 없다.** 20개 수준에서도 luna low가 99% 통과한다.
- **비밀글·포인트·프로필 수정은 넣을 이유가 없다.** 기본으로 다 막아서 신호가 없다.
- **참가자 프롬프트로 점수가 갈리는 지점은 "기능 문장에 규칙이 드러나지 않는" 결정이다.** CSRF, 로그인 제한, 시크릿, 세션, 헤더, SSRF, 업로드, XSS가 그렇다. 이 결정을 만드는 기능(로그인, 상태 변경 폼, 링크 미리보기, 업로드, 사용자 콘텐츠 렌더)은 유지해야 한다.
- **한계:** 명세당 n=5, 단발 생성, 중립 프롬프트만 썼다. 계약 루프나 참가자 보안 지시가 들어간 조건은 측정하지 않았다.

원자료: 생성 앱 `data/generated/sx-{a,b}{1..5}`, 계약 테스트와 프롬프트는 세션 스크래치패드 `specexp/`.
