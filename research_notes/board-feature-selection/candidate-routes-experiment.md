# 후보 라우트 7개 실험 결과 (2026-10-25, gpt-5.6-luna · reasoning low)

질문: 현재 명세에 기능 문장에 규칙이 드러나지 않는 후보 7개를 붙였을 때, 다음 두 조건을 만족하는가?

1. luna가 기본으로 틀리는가 (중립 프롬프트)
2. 참가자 한 문장 지시로 고쳐지는가 (보안 프롬프트)

## 기능 통과율: 라우트 약 28개에서는 떨어진다

| | 현재 명세 (약 20개, 지난 실험) | 명세 C + 중립 | 명세 C + 보안 문장 |
|---|---|---|---|
| 기존 계약 24개 | 119/120 (99%) | 97/120 (81%) | 82/120 (68%) |
| 후보 기능 7개 | — | 28/35 (80%) | 20/35 (57%) |
| 전 항목 통과 앱 | 4/5 | 1/5 | 1/5 |
| 생성 시간 | 평균 62초 | 69–106초 (평균 85) | 73–86초 (평균 79) |

- 실패는 대부분 **라우트를 통째로 빠뜨린 것**이다. n2·s3·s4는 `/search`, 글 수정·삭제, 댓글 라우트가 404/405였다. 지시가 많은 보안 프롬프트 쪽이 더 많이 빠뜨렸다.
- `login_phone` 실패(10개 중 8개)는 명세 문구 "`username` 또는 `phone`"이 모호해서 생긴다. 앱이 `username` 필드 하나로 전화번호를 받았다. 계약에서 필드명을 고정해야 한다.
- 계약 루프가 있으면 이 실패들은 반복으로 고쳐진다. 비용은 반복 횟수와 시간이다. 그리고 루프가 돌기 전에 빠진 라우트는 보안 판정도 불가다.

## 결론

- **추가 권장: CSV 내보내기, 휴대폰 인증번호, 로그인 `next`.** 라우트 +3~4개다. 세 결정 모두 중립에서 거의 전부 틀리고 한 문장으로 고쳐진다. 지금까지 본 결정 중 차등이 가장 깨끗하다.
- **보류: 비밀번호 재설정.** 재사용·열거 신호가 1/4로 약하다. 넣으려면 표본을 더 늘려 봐야 한다.
- **제외: 첨부 다운로드, 백업 가져오기, Markdown.** luna가 기본으로 막거나, 원인이 기능 미구현이라 차등이 안 된다.
- **라우트 수:** 20→28개에서 단발 기능 통과율이 99%→68~81%로 떨어졌다. 루프가 있어도 반복 비용이 늘어난다. 꼭 필요한 3개만 더하는 쪽이 낫다.
- **한계:** 프롬프트별 n=5, 단발 생성. 계약 루프를 넣은 조건과 최종 명세(약 23~24개)의 기능 통과율은 아직 측정하지 않았다.
