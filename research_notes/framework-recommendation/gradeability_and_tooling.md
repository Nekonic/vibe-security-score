# Gradeability and tooling: how accurately can security flaws be detected (static + dynamic) per web stack

Research date: 2026-10-24. Scope: Python (Flask, FastAPI, Django), Node/TS (Express, NestJS, Fastify, Next.js), Go (net/http, Gin), Java (Spring Boot), Ruby on Rails, PHP (Laravel/plain). Context: grader for small AI-generated SQLite board apps (static regex/AST + semgrep + gitleaks + osv-scanner; dynamic sqlmap/XSS/IDOR/CSRF/SSRF/headers/cookies/debug/rate-limit/CVE recompute).

Measured-vs-opinion legend: **[measured]** = number from a benchmark/paper/official doc; **[doc]** = official documentation statement (factual capability); **[opinion]** = author/vendor judgement.

## Q1. SAST precision/recall per language for web vulns (Semgrep, CodeQL, Bandit, njsscan, gosec, Brakeman, SpotBugs/FindSecBugs, PHPStan/Psalm)

### Takeaway
Across every language studied, published evaluations converge on the same shape: SAST tools are moderately-to-highly precise but have low recall on real-world code (roughly 12-48% detection), and no language has a clear, measured precision advantage. The deepest *tooling coverage* (CodeQL + Semgrep Pro cross-file + framework modeling) exists for Python, JS/TS, Java and Go; Ruby and PHP lag (CodeQL has no PHP; Semgrep Pro has no cross-file dataflow for Ruby/PHP). For Python specifically there is now a 2026 real-world CVE benchmark with per-tool numbers in which Semgrep had the best recall/F1 of the off-the-shelf tools.

### Cited Findings
- **Python, real-world CVE benchmark (PyFlow paper, arXiv 2608.07026, Aug 2026)** [measured]: 108 CVEs from 62 Python projects (206 program versions: 108 vulnerable, 98 patched), CWEs 77/502/94/79/22/89. Precision / Recall / F1: DevSkim 82.4/13.0/22.5; Dlint 72.5/26.9/39.2; **Bandit 60.0/27.8/38.0**; Bearer 62.3/35.2/45.0; **CodeQL 72.3/31.8/44.2**; **Pysa 0.0/0.0/0.0**; **Semgrep 65.7/40.7/50.3**; Snyk 80.0/11.9/20.7; PyFlow (research tool) 71.2/48.1/57.5. Semgrep was the best baseline. — [PyFlow, arXiv HTML](https://arxiv.org/html/2608.07026v1)
- Same paper: Python "provides no nominal type system that can resolve most call targets statically"; it names Django's metaclass-based models and Flask's decorator-registered routes as the dynamic-dispatch-heavy patterns; it states Bandit and Semgrep (OSS rules) are pattern-based and perform no flow-/context-/path-sensitive analysis; PyFlow's own misses came from incomplete library stubs and `setattr`-constructed attributes. — [PyFlow, arXiv HTML](https://arxiv.org/html/2608.07026v1)
- **Java, synthetic** (EASE 2024, "An Extensive Comparison of SAST Tools", ~1.5M test executions on a synthetic Java codebase) [measured]: SAST tools show "high precision" but "low recall" and detect a very narrow range of vulnerability types; authors explicitly contradict the folk belief that SAST is mostly false alarms. — [arXiv 2403.09219](https://arxiv.org/abs/2403.09219)
- **Java, real-world** (Li et al., ESEC/FSE 2023, "Comparison and Evaluation on SAST Tools for Java"; 7 free/OSS tools chosen from 161) [measured]: tools do well on synthetic benchmarks but "only 12.7% of real-world vulnerabilities can be detected". — [SMU InK record](https://ink.library.smu.edu.sg/sis_research/8976); DOI 10.1145/3611643.3616262
- **Multi-language (Java, C, Python)** (Zhou et al., arXiv 2407.16235, 2024; 15 SAST tools vs 12 LLMs, repo-level) [measured, aggregate only in abstract]: SAST tools "obtain low vulnerability detection rates with relatively low false positives"; LLMs detect 90-100% but with high false positives; ensembling mitigates both. — [arXiv 2407.16235](https://arxiv.org/abs/2407.16235)
- **JavaScript/Node** (Brito et al., 957 known npm vulnerabilities, 9 JS SAST tools incl. CodeQL and ODGen; cited secondhand in a 2026 arXiv paper) [measured, secondary]: CodeQL was best but detected only **31.3%**; low recall attributed to JS dynamic behaviour. Same 2026 paper notes CodeQL/SonarQube/Semgrep exclude dependencies by default, and ODGen suffers state explosion. — [arXiv 2601.10865 (SemTaint)](https://arxiv.org/html/2601.10865v1)
- ODGen (USENIX Sec 2023) [measured, own benchmark]: found 302/330 known vulns; on ~300k npm packages, 180 of 264 checked reports confirmed (68% confirmation of the sampled subset, not a global FP rate). — [Dark Reading](https://www.darkreading.com/cyber-risk/new-odgen-tool-unearths-180-zero-days-in-node-js-libraries)
- **Go** (arXiv 2604.24085, 2026, crypto-misuse only, 328 repos, 7,473 findings, 4 tools) [measured]: gosec produced 67.4% of all detections and 92.6% of its locations were unique to gosec; authors treat that as "false positive risk" and recommend focusing on overlapping detections. No web-injection precision data for gosec found. — [arXiv 2604.24085](https://arxiv.org/pdf/2604.24085)
- **Java OWASP Benchmark, old scorecards** (~2017 Contrast brief) [measured, outdated]: FindSecBugs v1.4.3 score 32%, SonarQube Java 3.5 33%, OWASP ZAP 18%, PMD 0%, commercial average 26% (score = TPR - FPR). — [Contrast tech brief PDF](https://contrastsecurity.com/hubfs/DocumentsPDF/WPtechbriefbenchmark0117.pdf?hsLang=en)
- **Semgrep vs CodeQL** (Doyensec, 2022-10-06) [measured but numbers only in charts; text summary]: on OWASP Benchmark Java, Semgrep (security-audit) "performed better, on average" than CodeQL, largely because CodeQL found nothing in three CWE areas; in a cross-tool test suite CodeQL detected more but with higher FP; 85% of files hit CodeQL DB-creation errors in that suite; on a Go project 63/74 files had CodeQL extraction errors while scoped Semgrep had 15/15 true positives. [opinion] CodeQL "might be a better choice" for FP-sensitive CI. — [Doyensec blog](https://blog.doyensec.com/2022/10/06/semgrep-codeql.html)
- **OWASP Benchmark for Python** exists (v0.1, 1,230 test cases, 14 vuln areas, preliminary) but I found no published per-tool scorecard for Semgrep/Bandit/CodeQL on it. — [OWASP BenchmarkPython repo](https://github.com/AppSec-Tool-Benchmarking/OWASP-BenchmarkPython); [OWASP Benchmark](https://owasp.org/www-project-benchmark/)
- **Semgrep language maturity** [doc]: Python, JavaScript, TypeScript, Java, Go, C# are GA with cross-file dataflow; Python/JS/TS/Java also have "framework-specific control flow". **Ruby and PHP are GA but listed with cross-function only (no cross-file dataflow)**. Pro rule counts: Python 710+, JS 250+, TS 230+, Java 190+, C# 170+, Go 80+, PHP 50+, Ruby 40+. CE (OSS) is limited to single-function analysis for most languages. — [Semgrep supported languages](https://docs.semgrep.dev/supported-languages); [Semgrep CE languages](https://docs.semgrep.dev/semgrep-ce-languages)
- **CodeQL coverage** [doc]: **PHP not supported**. Framework models include Python: Django, DRF, Flask, FastAPI, Starlette, Tornado, aiohttp; JS/TS: Express, Fastify, hapi, Koa, Nest.js, React, Vue (Next.js not listed); Java: Spring MVC, Struts, JAX-RS, JDBC/Spring JDBC/Hibernate/JPA; Ruby: Rails; Go: Gin, Chi, Echo, Gorilla mux, GORM, sqlx (net/http and database/sql not named on that page). DB libs: Python sqlite3 + SQLAlchemy listed; JS sqlite3 listed but **better-sqlite3 and Prisma not listed**. — [CodeQL supported languages and frameworks](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)
- Brakeman: no quantitative precision study found; maintainers' release notes repeatedly target FP reduction; confidence levels (High/Medium/Weak); heavy `method_missing` metaprogramming limits analysis [opinion]. — [Brakeman 1.8.3 release](https://brakemanscanner.org/blog/2012/11/13/brakeman-1-dot-8-3-released); [Big Nerd Ranch talk summary](https://bignerdranch.com/blog/tech-talk-on-brakeman)
- Bandit vs Semgrep [opinion, vendor]: Semgrep's own 2021 comparison conceded Bandit tends to report more "accurate" results, Semgrep's advantage being rule customizability. — [Semgrep blog 2021](https://semgrep.dev/blog/2021/python-static-analysis-comparison-bandit-semgrep)
- Semgrep self-reported 84% "benchmark true positive rate" for its ruleset on its own OSS-repo benchmark [vendor, not comparable to OWASP]. — [Semgrep Python docs](https://semgrep.dev/docs/languages/python)

### Inferences
- No measured evidence shows one language yields materially higher SAST precision for SQLi/XSS/SSRF/path traversal. The real differentiator is **coverage depth**: Python/JS/TS/Java/Go have both CodeQL framework models and Semgrep Pro cross-file taint; Ruby/PHP are weaker (PHP worst: no CodeQL, no Semgrep cross-file).
- Python is the only language with a fresh (2026) real-world per-tool table; its numbers (best F1 ~50% for Semgrep, CodeQL precision ~72%) confirm SAST alone cannot be trusted as the sole verdict — it should be a supporting signal, with dynamic confirmation for scored findings.
- For a grader that already uses Semgrep + custom Python AST checks, staying on Python keeps the strongest rule corpus (710+ Pro rules, the largest of any language) and lets the custom AST checks remain valid.
- Synthetic-vs-real gap (Li et al.: good on benchmarks, 12.7% real) suggests AI-generated small apps — which are closer to "synthetic" (short, idiomatic, few files) — are likely to sit at the *easier* end for SAST in every language. This is an inference, not measured.

### Gaps
- No published Semgrep/Bandit/CodeQL scorecard on OWASP BenchmarkPython; no current (2024+) OWASP Benchmark Java numbers for Semgrep/CodeQL in text form.
- No quantitative precision/recall study found for njsscan, Brakeman, PHPStan/Psalm taint mode, or gosec on web injection classes.
- The Li et al. 2023 per-tool table and the Brito et al. per-tool table were not retrieved directly (only abstract / secondhand figure).

## Q2. Is a single-file / small-app pattern easier to analyze in some ecosystems? Do decorators, DI, dynamic dispatch, middleware ordering hurt static precision?

### Takeaway
Yes, structure matters more than language: decorator-registered routes (Flask), metaclass models (Django), and DI/decorator wiring (NestJS, Spring) are explicitly cited as precision/recall killers for call-graph-based analyzers, while a single-file Flask/Express app whose routes, queries and templates are visible in one function is within reach even of single-function (Semgrep CE) analysis. Constraining the generation contract to a single-file, explicit-route, raw-`sqlite3` style is a bigger lever than switching language.

### Cited Findings
- Dynamic dispatch (Django metaclass models, Flask decorator-registered routes) forces resolvers to rely on name/annotation heuristics to find callees. — [PyFlow, arXiv HTML](https://arxiv.org/html/2608.07026v1)
- Semgrep CE "is limited to single-function analysis for most languages"; cross-file dataflow is a Pro feature. — [Semgrep CE languages](https://docs.semgrep.dev/semgrep-ce-languages)
- Doyensec (2022): Semgrep "works on a single file basis" by default and "lacks a full understanding of the code flow" for complex source-to-sink paths; CodeQL needs a buildable project and is stricter about parsing (extraction errors on many files). — [Doyensec blog](https://blog.doyensec.com/2022/10/06/semgrep-codeql.html)
- JS SAST recall limits attributed to "fundamental gaps in how current SAST tools model JavaScript's dynamic behavior"; CodeQL/Semgrep/SonarQube skip dependencies by default. — [arXiv 2601.10865](https://arxiv.org/html/2601.10865v1)
- An EditTime study reports CodeQL's detection rate drops significantly on single-file snippets (CodeQL's model relies on whole-program extraction). — [arXiv 2306.01754](https://arxiv.org/pdf/2306.01754)
- Brakeman analysis is limited by heavy metaprogramming (`method_missing`) [opinion]. — [Big Nerd Ranch](https://bignerdranch.com/blog/tech-talk-on-brakeman)
- CodeQL models Nest.js and Express/Fastify explicitly, but not Next.js; Python models cover Flask/Django/FastAPI/Starlette. — [CodeQL frameworks](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)

### Inferences
- Single-file apps help pattern tools (regex, AST, Semgrep CE) the most and hurt CodeQL the least among stacks it supports, because the full source-to-sink path lives in one file/function.
- NestJS (controllers + providers + DI + decorators/pipes/guards) and Spring Boot (annotations, beans, filter chains) push security-relevant behaviour (auth guards, CSRF filters, validation pipes) into configuration/decorators spread across files; regex/AST "is protection present?" checks become guess-prone there (high FP if absence is assumed, FN if presence is assumed). This is inference from the cited dynamic-dispatch findings, not a measured study.
- Middleware-ordering semantics (e.g., Express `app.use` order, Spring filter chain order, Django `MIDDLEWARE` list) are generally not modeled by pattern tools; a static check that "helmet/csrf is installed" cannot prove it runs before the route. Dynamic probes are the only low-FP way to verify these properties, independent of language.
- Next.js (React Server Components, server actions, API routes, client rendering) is the worst fit: not modeled by CodeQL, mixes client/server code, and renders HTML client-side (see Q4).

### Gaps
- No measured study directly compares SAST accuracy on single-file vs multi-module versions of the same app, or Flask vs NestJS vs Spring for an equivalent feature set.

## Q3. Dependency/CVE determinism: lockfiles, osv-scanner coverage, transitive tree size, reproducible installs

### Takeaway
Ecosystems with mandatory, fully-pinned lockfiles that include transitive deps (npm `package-lock.json`, Go `go.mod`/`go.sum`, `composer.lock`, `Gemfile.lock`, `uv.lock`/`poetry.lock`) give deterministic CVE input; plain `requirements.txt` with ranges does not (osv-scanner now resolves it via deps.dev, which may differ from the real install). npm's large transitive trees are a well-documented source of noise CVEs (dev-only, unreachable). The current grader's approach of recomputing CVEs from `pip freeze` inside the sandbox is already the most deterministic option for Python; the equivalent for npm would be `npm ls --all --omit=dev` from the installed tree.

### Cited Findings
- osv-scanner (v1 docs) supports `requirements.txt` (asterisked/partial), `Pipfile.lock`, `poetry.lock`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `go.mod`, `composer.lock`, `Gemfile.lock`, `pom.xml` (asterisked), `gradle.lockfile`, `Cargo.lock`, etc. — [osv-scanner v1 supported lockfiles](https://google.github.io/osv-scanner-v1/supported-languages-and-lockfiles/)
- osv-scanner v2 (March 2025) moved extraction to OSV-SCALIBR and added `uv.lock`, `bun.lock`, `deps.json`. — [Google Security Blog, v2 announcement](https://security.googleblog.com/2025/03/announcing-osv-scanner-v2-vulnerability.html)
- v2.3.5+ enables deps.dev-based transitive resolution for `requirements.txt`; Maven `pom.xml` transitive resolution via deps.dev by default (`--no-resolve` to disable). — [osv-scanner releases](https://github.com/google/osv-scanner/releases); [oneuptime guide, 2026-07-23 (secondary)](https://oneuptime.com/blog/post/2026-07-23-osv-scanner-dependency-discovery/view)
- deps.dev resolution of `requirements.txt` ignores `-c` constraints and pip index options and "is not a target-platform pip install"; version ranges (e.g. `library>=2,<4`) describe many possible installs and cannot prove which vulnerable code is deployed → FP/FN risk. [secondary] — [oneuptime: manifest vs lockfile](https://oneuptime.com/blog/post/2026-07-23-manifest-vs-lockfile-osv/view); [oneuptime: requirements FP](https://oneuptime.com/blog/post/2026-07-23-requirements-false-positives-osv/view)
- npm audit noise: npm's Kat Marchán agreed criticism of default audit FP behaviour "isn't wrong" (critic claimed ~99%, unmeasured) (Register, 2021-07). — [The Register](https://www.theregister.com/2021/07/09/npm_audit_security/)
- An npm RFC proposed letting maintainers assert non-affectedness because transitive-dependency noise makes people ignore `npm audit`. — [npm RFC PR #422](https://github.com/npm/rfcs/pull/422/files/ec911efa0fb02624a27b1afadd295b1ff5cf4728)
- GitHub Dependabot auto-dismisses npm devDependency alerts; GitHub says this cuts npm alert volume by about 15% [measured, vendor]. — [GitHub blog](https://github.blog/security/supply-chain-security/dependabot-relieves-alert-fatigue-from-npm-devdependencies)
- Semgrep Supply Chain offers reachability analysis for all 8 major languages; C# requires `packages.lock.json`. — [Semgrep supported languages](https://docs.semgrep.dev/supported-languages)
- A vendor guide claims ~80% FP for npm audit on a typical project, without methodology [unverified]. — [PkgPulse](https://www.pkgpulse.com/guides/why-npm-audit-is-broken)

### Inferences
- For grading, CVE determinism depends less on the manifest format than on *scanning the actually installed set inside the sandbox*. Python: `pip freeze`/`uv pip freeze` (already done). Node: `npm ls --all --json --omit=dev` or the generated `package-lock.json`. Go: `go list -m all` / `govulncheck` (call-graph reachability, reduces FP). Java: resolved Maven/Gradle tree. PHP/Ruby: `composer.lock`/`Gemfile.lock` are generated on install and fully pinned.
- Node apps will typically pull hundreds of transitive packages even for Express + a SQLite driver + session middleware, producing more CVE hits that are unreachable or dev-only; without reachability filtering, Node raises FP in a "vulnerable dependencies" category relative to a minimal Flask app. Python small apps (Flask + Werkzeug + Jinja2 + itsdangerous + MarkupSafe + click + blinker) have a small, well-curated tree. This is inference; I found no measured per-ecosystem transitive-count comparison.
- Go has the best-in-class reachability tooling (govulncheck, symbol-level) which would give the lowest dependency FP — but Go was not otherwise favoured by SAST/IAST evidence.
- Native-extension installs (e.g., Node `sqlite3`/`better-sqlite3` building from source, Python wheels) are a sandbox reproducibility risk; Python's stdlib `sqlite3` avoids any DB-driver install entirely.

### Gaps
- No measured comparison of average transitive dependency counts or CVE-noise rates per ecosystem for equivalent small apps.
- Official v2 osv-scanner "supported artifacts" page not retrieved; transitive-resolution details come from release notes plus a secondary blog.

## Q4. Dynamic testing determinism: error/debug signatures, default headers, session cookie names, CSRF conventions; DAST FP/FN by framework

### Takeaway
Server-rendered HTML frameworks with a single canonical session/CSRF convention (Django, Rails, Laravel) are the most machine-recognizable; Flask is recognizable for sessions/debugger but CSRF depends on whichever extension (or none) the model picks; Express/Fastify/NestJS vary widely by middleware choice; SPA/JSON-API stacks (Next.js, NestJS APIs) hide reflected/stored XSS from HTML-response checks and make form-based CSRF/sqlmap crawling harder. Framework defaults also differ in which security headers are on by default, which directly moves baseline scores.

### Cited Findings
- Django 6.1 docs [doc]: `CSRF_COOKIE_NAME='csrftoken'`, `CSRF_COOKIE_HTTPONLY=False`, `SECURE_CONTENT_TYPE_NOSNIFF=True` (SecurityMiddleware emits `X-Content-Type-Options: nosniff`), `SECURE_CROSS_ORIGIN_OPENER_POLICY='same-origin'`, `DEBUG` defaults False but `startproject` template sets `DEBUG = True`. — [Django settings](https://docs.djangoproject.com/en/stable/ref/settings/)
- Django debug 500 page is rendered by a dedicated minimal template engine from `django.views.debug` (stable, recognizable page); strict CSP breaks its inline CSS/JS. — [Django debug source](https://docs.djangoproject.com/zh-hans/2.2/_modules/django/views/debug/); [Django ticket 33180](https://code.djangoproject.com/ticket/33180?format=tab)
- Werkzeug's interactive debugger replaces the traceback page with source view + interactive console (Flask debug mode). — [PyPI django-debugging](https://pypi.org/project/django-debugging/0.1a2/); [djangosnippets](https://djangosnippets.org/tags/debugging/)
- express-session [doc]: default cookie name `connect.sid`; HttpOnly on by default; `Secure` not set; `SameSite` not set by default. — [expressjs/session README](https://github.com/expressjs/session)
- Laravel 13.x [doc]: `PreventRequestForgery` middleware in the `web` group by default; **first checks `Sec-Fetch-Site`** (same-origin → allowed without token), falls back to `_token` field / `X-CSRF-TOKEN` header; `XSRF-TOKEN` encrypted cookie sent on every response; token mismatch → **419**, origin-only mode → 403; `Sec-Fetch-Site` only sent over HTTPS, so on HTTP it falls back to token validation. — [Laravel CSRF docs](https://laravel.com/docs/csrf)
- ZAP vs OWASP Benchmark (daily run, 2026 page) [measured]: Command Injection 251 tests, page reports 77% pass; per-row tally ≈54% TPR, 0 FP rows. Other categories not shown on the page. — [ZAP benchmark page](https://www.zaproxy.org/docs/scans/benchmark/)
- ZAP's old Benchmark score: 18% (≈2017). — [Contrast tech brief](https://contrastsecurity.com/hubfs/DocumentsPDF/WPtechbriefbenchmark0117.pdf?hsLang=en)
- SPAs load content without full page refresh, complicating vulnerability identification; ZAP needs the AJAX Spider for JS-rendered content; DOM XSS requires dedicated DOM-based checks [secondary/educational]. — [IUST thesis record](https://dl.iust.ac.ir/Inventory/14/14333.htm); [Cyberly SPA guide](https://www.cyberly.org/en/how-do-you-use-owasp-zap-to-test-the-security-of-a-single-page-application-spa/index.html); [Pluralsight DOM XSS lab](https://www.pluralsight.com/labs/aws/dom-based-security-testing-with-zap)
- Nuclei templates are YAML matchers over responses; the official library (12,000+ templates) includes exposed debug endpoints, but I could not confirm specific Werkzeug/Laravel/Django template IDs. — [Nuclei templates concept](https://www.mintlify.com/projectdiscovery/nuclei/concepts/templates)

### Inferences
- **Debug detection FP/FN**: Django's technical-500 page and Werkzeug's debugger are single, stable, framework-owned signatures → near-zero-FP string matching. Laravel (Ignition) and Rails (dev error page) are similarly canonical. Express/Fastify/NestJS have no canonical debug page: Express's default handler prints a stack trace in non-production `NODE_ENV`, but apps often install custom handlers → more heuristic matching (higher FN). Spring Boot's Whitelabel page with `server.error.include-stacktrace` is canonical but configuration-dependent. (Framework behaviours beyond the cited docs are from general knowledge and should be verified before relying on them.)
- **Cookie/session probes**: canonical names (`sessionid`/`csrftoken` in Django, `session` in Flask, `connect.sid` in express-session, `laravel_session`/`XSRF-TOKEN` in Laravel, `JSESSIONID` in Spring, `_<app>_session` in Rails) let a grader identify *the* session cookie reliably; Node stacks often use JWT-in-localStorage or custom cookie names chosen by the model → cookie-flag checks can't be sure which cookie is the auth cookie (FP/FN).
- **CSRF probes**: Laravel's new `Sec-Fetch-Site` origin check means a probe that omits the header or sends it over plain HTTP exercises only the token path; a probe that copies browser headers (`Sec-Fetch-Site: same-origin`) would be wrongly accepted. Probes should explicitly send `Sec-Fetch-Site: cross-site` and `Origin: http://evil` and treat 403/419 as "protected". Similar origin/Sec-Fetch checks are emerging in other frameworks, so the CSRF probe should be header-explicit regardless of stack.
- **XSS probes**: reflection-based checks are only reliable when the server renders HTML (Jinja2, Django templates, ERB, Blade, Thymeleaf, EJS). For React/Next.js client rendering, payloads arrive in JSON and are escaped by React unless `dangerouslySetInnerHTML` is used; HTML-reflection checks would then report FN for real DOM XSS and FP-risk for JSON echoes. Requiring server-rendered HTML templates in the app contract keeps XSS probing deterministic.
- **sqlmap**: works best on form/query parameters with observable boolean/error/time differences; SQLite + Python `sqlite3` produce consistent `sqlite3.OperationalError` text when errors are surfaced. JSON-body APIs need explicit request templates (`-r` or `--data` with JSON), which the grader would have to derive per app → more brittle on JSON-API stacks.
- **Default security headers** vary by framework (Django ships nosniff/COOP/X-Frame-Options via middleware; Express ships none and advertises `X-Powered-By`; Spring Security ships several), so header scores partly reflect framework choice rather than model effort — the rubric-calibration memory already wants "framework-default baseline ≈10-30"; that baseline must be recalibrated per framework if more than one is allowed.

### Gaps
- No measured per-framework DAST FP/FN data (ZAP/Nuclei/sqlmap) found; ZAP's public Benchmark page shows only command injection.
- Could not verify specific nuclei template coverage for Werkzeug/Django/Laravel/Rails debug pages.
- Default header sets for Spring Security, Rails, Laravel, Express were not fetched from primary docs in this pass.

## Q5. Runtime instrumentation (IAST / sink observation) for near-zero-FP SQLi/XSS confirmation — which ecosystem is easiest?

### Takeaway
Java has the most mature agent-based IAST (Contrast, Datadog, etc.), but for a self-hosted grader on small SQLite apps, **Python is the easiest**: stdlib `sqlite3.Connection.set_trace_callback` reports every SQL statement actually executed, so a grader can inject a unique canary and confirm SQLi by seeing it outside a bound parameter — with no third-party agent, via a `sitecustomize.py` monkeypatch of `sqlite3.connect`. Node is second (require/import hooks; Datadog IAST covers SQLi/SSRF/path traversal but not XSS in Node or Python). PHP/Ruby/Go have the weakest off-the-shelf options.

### Cited Findings
- Python `sqlite3.Connection.set_trace_callback(cb)` [doc]: invoked "for each SQL statement that is actually executed by the SQLite backend", single `str` argument (the statement), also fires for internal transaction statements and triggers; available since 3.3. Docs do not state whether bound parameters are expanded. — [Python sqlite3 docs](https://docs.python.org/3/library/sqlite3.html)
- Python audit hooks (PEP 578, 3.8+): `sys.addaudithook` receives events such as `sqlite3.connect` (path arg), `sqlite3.enable_load_extension`, `sqlite3.load_extension` (3.11+ tables); audit hooks observe events, not data flow. — [Python audit events table 3.12](https://docs.python.org/3.12/library/audit_events.html)
- Datadog Runtime Code Analysis (IAST) [doc]: rule matrix — SQL injection, SSRF, path traversal, command injection, insecure cookie, header injection: Java/.NET/Node/Python all TRUE; **XSS: Java and .NET only (Node FALSE, Python FALSE)**; reports only when tainted input is confirmed to reach a sink. — [Datadog IAST](https://docs.datadoghq.com/security/code_security/iast/)
- Datadog IAST compatibility [doc]: Python tracer ≥3.18.0 with Django 2.2+, FastAPI 0.86+, Flask 1.1+, "all generic SQL databases including SQLite"; Node tracer ≥4.18.0/5.0.0 with Express ≥4, Fastify ≥2, **Next.js listed without IAST support**, DBs mysql/mysql2/pg/mongodb-core/Sequelize (no sqlite3/better-sqlite3 listed); Java tracer ≥1.15.0 with Spring MVC/WebFlux/Boot, JDBC. NestJS not mentioned. — [Datadog IAST setup](https://docs.datadoghq.com/security/code_security/iast/setup/)
- Third-party summary lists Datadog Python IAST as "preview" [secondary, conflicts with official page which shows no preview label for Python IAST rules]. — [AppSecSanta Datadog IAST](https://appsecsanta.com/datadog-iast)

### Inferences
- **Python (best for this grader)**: a `sitecustomize.py` placed on `PYTHONPATH` in the sandbox can wrap `sqlite3.connect` to attach `set_trace_callback`, logging executed SQL to a file. The dynamic SQLi probe sends a unique canary like `zz'"q1x`; if the trace shows the canary inside the SQL text as anything other than a parameter value (`?`/`:name` placeholders), SQLi is confirmed with essentially no FP — even when the app swallows errors (fixes sqlmap FN on blind/error-suppressed endpoints). Similar wrappers on `jinja2.Template.render` / `markupsafe` (autoescape off, `|safe`, `Markup()`), `subprocess`, `open`, `requests/urllib` give canary-based XSS/command-injection/path-traversal/SSRF confirmation. Limitation: works when the app uses stdlib `sqlite3` or SQLAlchemy over it; would need re-validation for other drivers.
- **Node**: `node --require`/`--import` preload can monkeypatch `sqlite3`/`better-sqlite3` `prepare/exec/all`, `child_process`, `fs`, `http.request`; feasible but driver choice varies per generated app (sqlite3, better-sqlite3, Prisma, Sequelize, Knex), so the hook surface is larger and less uniform. Datadog IAST does not list sqlite drivers or XSS for Node.
- **Java**: java agents (byte-code instrumentation) are the most mature commercial IAST route (Datadog covers XSS in Java), and JDBC is a single choke point, but JVM start-up/build time and Spring complexity cost sandbox time and AI-generation reliability.
- **Go**: no runtime monkeypatching; would require wrapping `database/sql` drivers at build time — hardest to instrument without modifying generated code.
- **PHP/Ruby**: possible via extensions (PHP) or `Module#prepend` (Ruby), but no first-party Datadog IAST coverage found for either in this pass.
- A runtime sink log also enables the "minimize false positives" principle: only penalize when the sink actually received attacker-controlled, unescaped data.

### Gaps
- Whether `set_trace_callback` text includes expanded bound values is not stated in the docs (SQLite's `sqlite3_trace` historically shows the unexpanded SQL; verify empirically — it matters for canary interpretation: placeholders mean safe).
- No published FP rates for IAST products per language found; Contrast/Datadog accuracy claims not retrieved.
- Node `--import`/`module.register` hook docs and Ruby/PHP IAST options were not researched in this pass.
