# vibe-security-score — Architecture

Booth game: a participant writes a prompt → the server runs **Codex CLI** (operator's
ChatGPT login) to generate a **Flask board app** → the grader auto-scores that code in an
isolated container → the UI shows score/grade. Participants never touch code.

## Fixed stack (do not confuse)

| Concern | Tech | Notes |
|---|---|---|
| Grader web / queue / dashboard | **Django** (`grader/`, project package `grader/core/`) | Operator server. The grading engine itself imports no Django. |
| Participant-generated app | **Flask** | The grading *target*, generated by Codex. |
| Participant app execution | **`python:3.11-slim` container** | Non-root (uid 10001), memory/cpu/pids-limited, boot timeout. **Network stays ON.** |

The grader host env and the participant Flask env are **never shared**: the participant
`requirements.txt` (possibly vulnerable/typosquatted) installs **only inside the container**.

## Prompt model (system + participant)

The Codex prompt is assembled from two parts in `submissions/views.py::_build_prompt`:

- **System prompt** — `config/default_prompt.md`, a **fixed, server-side** spec defining the
  app contract (endpoints, user fields incl. `email`, `id=1` admin, post fields `title`/`content`).
  Rendered read-only in the left panel; the participant cannot edit it.
- **Participant prompt** — free text the participant writes (right panel). This is the lever
  they are actually scored on.

Final prompt = `system_prompt + "\n\n" + participant_prompt`. Keeping the spec server-side
guarantees the app contract the dynamic probes assume (see [APP_CONTRACT.md](APP_CONTRACT.md))
cannot be altered by the participant.

## Four parts

1. **Web UI (Django, `grader/`)** — `Submission` model + state machine
   (`queued → generating → scoring → done | failed | rate_limited`), all transitions via
   `submissions/state.py`. Participant flow: two-panel submit → poll status + queue position
   (`status_json`) → result (per-item ✔/✘ + 감점 사유 + 부분 점수 + 등급, built by
   `_category_groups`). Public leaderboard at `/ranking/` (`views.leaderboard`, viewable
   without login). A **real-time generation view** tails redacted Codex activity
   (`generation_events_json`). Operators get the Django admin plus a staff-only **재채점**
   (re-grade) button. Operator accounts use a custom `accounts.Operator` user model with
   **no email column** (email is a participant-app concept). Bootstrap UI vendored offline.

2. **Codex runner (`codex_runner/`)** — `runner.generate` drives `codex exec`
   (non-interactive), prompt via **stdin**; flags `--sandbox workspace-write
   --skip-git-repo-check --ephemeral --json --ignore-user-config --ignore-rules`. Harvests
   `app.py`/`requirements.txt`/`templates/` into `data/generated/<id>/` and writes `prompt.md`.
   **ChatGPT auth only** — `OPENAI_API_KEY`/`CODEX_API_KEY` blanked, no API-key fallback.
   `codex.model` empty ⇒ the account's default model (API-only ids like `gpt-5-codex` are
   rejected by ChatGPT-account auth). Serial use (5h rolling limit); a per-run wall-clock
   timeout kills the process tree. The JSONL stream is read **live** (`event_sink`);
   `codex_runner/activity.py` **redacts** each event (strips temp-workdir/host paths, drops
   command output) into `events.jsonl`, tailed read-only by the result page. The raw
   `transcript.json` stays operator-only. On Windows the npm `.cmd` shim runs via `cmd /c`;
   real generation needs a Linux/macOS/WSL sandbox (`python -m codex_runner.smoke`).

3. **Grading engine (`scoring/`)** — pure-Python (no Django import), standalone-testable.
   `grade.py::grade_submission` = static + dynamic → `aggregate.combine_scores` → report.
   - **(A) Static** (`static/runner.py`, offline) — source checks (`source_checks.py`):
     hardcoded secrets, `debug=True`, password hashing, raw-vs-parameterized SQL, XSS template
     sinks, cookie flags. OWASP defense-in-depth (`owasp_checks.py`): security headers, CSRF,
     CSP, transport security, weak default secret, insecure deserialization, security logging,
     SSRF sink. Dependencies (`dependency_checks.py`): CVE (OSV CLI or local snapshot) +
     typosquatting + hallucinated-package. Optional external tools (`tools.py`:
     gitleaks/semgrep/osv-scanner) skip cleanly when disabled.
   - **(B) Dynamic** (`dynamic/runner.py`) — boot the app in the container (`container.Sandbox`)
     and attack with `requests`. `functional` runs first (drives the gate; wrong-password
     rejection judged by **auth state**, not status code — form apps 200-rerender the login
     form). Then `idor_profile` (2-account cross-access on `email`), `access_control_admin`,
     `stored_xss`, `reflected_xss`, `sqli` (sqlmap or built-in oracle), `transport_security`,
     `rate_limiting`, `weak_password_policy`, `verbose_errors`, and `session_forgery` (forge a
     Flask cookie under a weak `SECRET_KEY`, report-only). CVE is **re-measured** against the
     container's `pip freeze` to catch transitive vulns. Untestable checks are **skipped**
     (excluded from the score), never scored 0. Timeouts throughout; container teardown in
     `finally`.

4. **Orchestrator (`grader/submissions/orchestrator/`)** — one worker (`run_worker`):
   **serial generation** (global lock — shared ChatGPT limit) feeding **bounded-parallel
   scoring** (isolated containers, `scoring_concurrency`). `process_one` dispatches
   **re-grade vs generate**: a `regrade_only` submission re-scores its existing `workdir` and
   **never calls Codex** (it fails if the code is gone); otherwise generate → score.
   Retry/backoff; rate-limit holds are re-queued (not dropped); an auth failure sets a global
   operator alert with no retry storm. A one-time orphan sweep at **startup** (safe — nothing
   in flight) replaces a separate janitor.

## Scoring

Each check yields 0–100. `aggregate.combine_scores`:

1. **Category score** = weight-normalized average of that category's checks (skipped checks excluded).
2. **Final** = category scores weighted by normalized category weights, renormalized over the
   *present* categories (a static-only run scores on static alone). `raw_score` is captured here.
3. **Critical penalties** (`_apply_critical_penalties`) — failed **critical** checks *subtract*
   fixed points from the final (stacking, floored at 0). A defect exploitable app-wide costs
   real points instead of being averaged away:

   | check | penalty | check | penalty |
   |---|---|---|---|
   | `sqli` | −25 | `weak_default_secret` | −15 |
   | `debug_true` | −20 | `reflected_xss` | −12 |
   | `access_control_admin` | −20 | `csrf_protection` | −6 |
   | `stored_xss` | −18 | | |

   `session_forgery` (weight 0) folds its live evidence into `weak_default_secret` (no double
   count). Each penalty carries a `severity` + `repro` shown on the result screen.
4. **Gate caps** (a ceiling applied *after* penalties): boot failure → cap `0`;
   functional-gate failure (signup/login/create-post) → cap `40`.

**Grade bands** (final ≥ min, from `grades`): `미흡 ≥0` · `통과 ≥60` · `우수 ≥80` · `최고 ≥95`.
PASS requires no boot/functional failure **and** final ≥ 60. Security items are never disclosed
pre-grading — only as penalty reasons on the result screen.

All weights/thresholds/penalties/gate-caps/grade-cuts live in one file:
[`config/scoring.yaml`](../config/scoring.yaml) — **nothing hardcoded in logic**. The 8
categories and weights (already summing to 100) are pure config; re-bucketing a check is a YAML edit:

| category | weight | category | weight |
|---|---|---|---|
| `functional` | 20 | `xss` | 10 |
| `auth` | 15 | `security_config` | 10 |
| `sqli` | 15 | `dependencies` | 10 |
| `input_validation` | 10 | `ai_security` | 10 |

## Sandbox (`sandbox/`)

`python:3.11-slim`, non-root (uid 10001), memory/cpu/pids limits, network ON. `entrypoint.sh`
copies the app to a writable dir and `pip install --user -r requirements.txt` (non-fatal). A
`sitecustomize.py` on `PYTHONPATH` monkeypatches `Flask.run` to bind `0.0.0.0:$APP_PORT` with
the reloader off — generated apps commonly `app.run(debug=True)` (binds 127.0.0.1, unreachable
through Docker's port map) — while keeping `debug` so debug-page vulns still score.
`Sandbox.pip_freeze()` feeds the transitive-CVE re-measurement.

## Repo layout

```
config/scoring.yaml         # THE single scoring config
config/default_prompt.md    # fixed system prompt (app spec)
scoring/                    # grading engine (pure python): static/ + dynamic/
codex_runner/               # codex exec wrapper + activity redaction (+ smoke.py dev test)
grader/                     # Django project (package grader/core/); apps: submissions, accounts
grader/submissions/orchestrator/   # DB queue backend + pipeline (driven by run_worker)
sandbox/                    # Dockerfile + entrypoint.sh + sitecustomize.py
samples/vulnerable_board/   # weak Flask app (debug/CSRF/headers/weak-secret gaps) — grading fixture
samples/secure_board/       # hardened Flask app (CSRF, hashing, env secret, headers) — grading fixture
data/                       # generated apps + codex transcripts + fixed snapshots (OSV, popular pkgs)
deploy/                     # prod: gunicorn + systemd + nginx (see deploy/README.md)
pyproject.toml / uv.lock    # deps (uv)
```

## Environments

Prod = Ubuntu, deps via **uv**, web on gunicorn + systemd behind nginx, **PostgreSQL** DB
(parallel scoring writes). The grading tools (`osv-scanner`/`gitleaks`/`semgrep`/`sqlmap`) are
required in default mode (`--dev` swaps in built-in offline checks — dev only). Verify a deploy
by grading `samples/vulnerable_board/` (planted `SECRET_KEY`, IDOR, stored XSS, admin access,
SQLi must all lose points). Full deploy: [deploy/README.md](../deploy/README.md).
