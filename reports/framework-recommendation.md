# Flask에 남고 계약 루프로 추측을 지워라

결론부터 말하면, 엔드포인트를 HTTP 계약 루프로 완전히 고정한다는 전제에서 **1순위는 Flask 유지**, **대안은 FastAPI(Jinja2 서버 렌더링 + 쿠키 세션 강제 조건)** 다. **Django·Rails·Laravel·Spring Boot·Next.js·NestJS·plain PHP는 비추천**이고, Express와 Go는 쓸 수는 있지만 이식 비용 대비 얻는 것이 없다. 이유는 계약 루프가 판도를 바꾸기 때문이다. FastAPI의 최대 장점은 Pydantic과 자동 OpenAPI 덕분에 계약을 잘 지킨다는 것인데, 루프가 어느 프레임워크에서든 계약 적합성을 보장하므로 이 장점은 거의 상쇄된다. 그러면 남는 판단 기준은 두 가지다. 참가자 프롬프트에 따라 결과가 갈리는 폭(변별력)과 취약점을 HTTP·런타임에서 결정적으로 관측할 수 있는지(정확도)다. 두 축 모두에서 Flask가 가장 앞선다. BaxBench에서 Flask의 XSS 발생률은 보안 지시 수준에 따라 **.99 → .90 → .44**로 떨어져 가장 프롬프트에 민감한 프레임워크 중 하나였다. 반대로 NestJS는 .93 → .86으로 거의 움직이지 않았고, Rails와 Lumen은 처음부터 낮았다 ([BaxBench v3](https://arxiv.org/html/2502.11844v3)). 레포 코드를 분석해 보면 지금 남아 있는 오탐/미탐의 대부분은 프레임워크가 아니라 두 곳에서 나온다. 하나는 계약이 모호해서 생긴 추측(필드명 뿌리기, id 탐색, 관리자 페이지 키워드 판정)이고, 다른 하나는 정적 "존재 검사" 정규식이다. 앞의 것은 계약 루프로 없어지고, 뒤의 것은 동적 프로브로 바꾸면 없어진다. 프레임워크를 바꾸면 이 두 문제는 그대로 남고, Flask 전용 critical 감점 41점이 조용히 사라져 채점기가 체계적으로 관대해진다. 따라서 투자 순서는 "프레임워크 교체"가 아니라 "계약 루프 → 휴리스틱 제거 → 정적 검사의 동적 전환"이어야 한다.

## 엔드포인트를 고정하면 남는 오탐원은 프레임워크가 아니라 정적 존재 검사다

레포의 점수 구조부터 보면 결론이 분명해진다. 루브릭 100점 중 **약 52점은 어떤 프레임워크에도 그대로 쓸 수 있는 HTTP 프로브**에서 나온다. 기능 게이트, IDOR, 관리자 접근, 권한 상승, SSRF 콜백, sqlmap, stored/reflected XSS, 업로드, rate limit, 런타임 헤더·쿠키가 여기에 속한다. 나머지는 **약 28점이 Python/Flask 문법용 정규식 정적 검사**, **10점이 pip/PyPI에 묶인 의존성 풀**, **10점이 Python/Werkzeug 시그니처에 묶인 `verbose_errors`** 다 ([config/scoring.yaml:12-50, 303-528](../config/scoring.yaml) 기준 산술). 그런데 HTTP 프로브의 오탐/미탐을 만드는 장치들은 대부분 앱 인터페이스를 *추측*하려고 존재한다. 글 작성 때 `title, content, body, text`를 한꺼번에 보내는 것은 "앱마다 본문 필드명이 갈리기" 때문이다 ([scoring/shared/http.py:57-61](../scoring/shared/http.py)). 비밀번호 입력란이 보이면 로그아웃 상태로 보는 `_looks_like_login_form` 오라클 ([http.py:89-98](../scoring/shared/http.py))도 같은 이유로 있고, `관리자`·`admin dashboard` 같은 키워드로 관리자 페이지를 가려내는 `_looks_like_admin` ([http.py:295-322](../scoring/shared/http.py))은 계약 문서 스스로 "휴리스틱 추측 → FP/FN"이라고 인정한다 ([docs/APP_CONTRACT.md:166](../docs/APP_CONTRACT.md)). 최근 커밋 1530d6f에서 `object_authorization`과 `comment_authorization` BOLA 프로브를 삭제한 것도 결국 계약 모호성 때문이었다. 응답에 id가 드러나지 않는 앱이 grader의 탐색 실패 탓에 누명을 쓰거나 판정이 스킵되었기 때문이다 ([scoring/checks/A01_broken_access_control.py:9-13](../scoring/checks/A01_broken_access_control.py)).

가장 위험한 미탐도 여기서 나온다. `/posts`, `/posts/<id>`, `/search`가 JSON을 돌려주면 두 XSS 프로브가 판정을 건너뛰고(`continue`), 그 앱은 **방어한 것으로 인정**된다 ([scoring/checks/A05_injection_xss.py:213-214, 290-292, 303-304](../scoring/checks/A05_injection_xss.py)). 현재 프롬프트는 *요청*에 대해서만 "JSON과 form 요청을 모두 지원한다"고 할 뿐, 페이지 응답 형식은 정하지 않는다 ([config/default_prompt.md:44](../config/default_prompt.md)). 계약 루프가 긍정 경로만 고정해도 이 장치들은 모두 결정적 판정으로 바뀐다. 고정할 항목은 `POST /posts` → `201 {"id":n}`, 로그인 시 `{"id":n}`, `GET /me` → 인증 시 `200 {id, username}`, 관리자의 `GET /admin/users` → 기계 판독용 마커, 업로드 → `{"url":...}`, 그리고 페이지의 `text/html` 응답이다. BOLA 프로브를 삭제한 전제(응답 형태 모호성)도 함께 사라진다.

계약 루프로도 고칠 수 없는 것은 세 종류다. 첫째, **정적 존재 정규식**이다. `csrf_protection`은 서버 측 검증 없이 토큰 문자열만 있어도 점수를 준다 ([scoring/README.md:157-159](../scoring/README.md)). `password_hashing`은 "bcrypt"라는 단어만 있어도 강한 해시로 인정한다 ([scoring/checks/A04_cryptographic_failures.py:116-165](../scoring/checks/A04_cryptographic_failures.py)). 둘째, **언어에 묶인 시그니처**다. 에러 트레이스 문자열, Flask 쿠키 서명기로 하는 세션 위조, pip 생태계가 여기에 해당한다. 셋째, **보안 기본값이 체크를 상수로 만드는 프레임워크**에서 생기는 변별력 상실이다. 정적 분석의 한계 자체는 언어와 무관하다. 레포가 정적 `ssrf_sink`를 삭제하면서 "실제 데이터플로 분석 없이는 방어된 구현과 공격 가능한 구현을 구분할 수 없다"고 적은 것이 그 증거다 ([A01:5-7](../scoring/checks/A01_broken_access_control.py)). 그러니 프레임워크를 바꿔도 첫째 문제는 그대로 남고, 둘째 문제는 처음부터 다시 쌓아야 하며, 셋째 문제는 오히려 커진다.

## 변별력은 기본값이 비어 있는 프레임워크에서 나온다

부스 채점기에서 변별력이란 "참가자가 프롬프트로 바꿀 수 있는 독립적인 보안 결정이 몇 개인가"다. Django·Rails·Laravel·Spring Security는 CSRF, 템플릿 이스케이프, 파라미터화 ORM, 비밀번호 해시 도우미, 강화된 세션 쿠키를 **기본으로 켠다**. Django는 CSRF 미들웨어, 자동 이스케이프, 파라미터화 queryset, X-Frame-Options, `ALLOWED_HOSTS`를 기본 제공한다 ([Django security](https://docs.djangoproject.com/en/stable/topics/security/)). Rails는 새 앱에서 forgery protection과 쿠키 암호화가 기본이고 보안 헤더 다섯 개를 보낸다 ([Rails Security Guide](https://guides.rubyonrails.org/security.html)). Laravel은 `web` 그룹에 CSRF 미들웨어가 기본으로 들어 있다 ([Laravel 12 CSRF](https://laravel.com/docs/12.x/csrf)). 이런 프레임워크에서는 대충 쓴 프롬프트도 CSRF·XSS·SQLi 방어를 공짜로 얻으므로, 현 루브릭의 가장 무거운 체크들이 모든 참가자에게 똑같이 통과로 수렴한다. 레포는 이미 "프레임워크 기본값만 쓴 앱이 10–30점"이 되도록 가중치를 보정해 두었는데, 이런 프레임워크로 옮기면 그 보정이 깨진다.

반대로 Flask는 거의 모든 것을 작성자, 즉 AI와 참가자에게 맡긴다. `SESSION_COOKIE_SAMESITE` 기본값은 None, `SESSION_COOKIE_SECURE`는 False, `SECRET_KEY`는 None이고 업로드 크기 제한과 호스트 검증도 기본으로 꺼져 있다 ([Flask 3.1 config](https://flask.palletsprojects.com/en/stable/config/)). `SECRET_KEY=None`이면 세션이 동작하지 않으니 AI는 비밀키를 어떻게 다룰지 *반드시* 결정해야 하고, 바로 그 결정이 현재의 약한 비밀키 → 세션 위조 체크를 깨끗하게 증명 가능한 레버로 만든다. Werkzeug 디버거가 켜진 채 `/console`이 노출되면 RCE로 이어진다 ([HackTricks: Werkzeug](https://book.hacktricks.xyz/network-services-pentesting/pentesting-web/werkzeug)). 이 때문에 `debug_true`는 이진적이고 결정적인 고심각도 체크가 되며, 다른 후보 대부분에는 이에 해당하는 체크가 없다. FastAPI의 기반인 Starlette `SessionMiddleware`는 기본이 `same_site='lax'`, 항상 HttpOnly이고 CSRF 미들웨어는 내장하지 않는다 ([Starlette middleware docs](https://raw.githubusercontent.com/encode/starlette/master/docs/middleware.md)). 레버가 Flask보다 하나둘 적은 셈이다. Express는 레버가 가장 많지만, `csurf`가 2025년 5월 공식 폐기된 뒤 내장 대체재가 없다 ([Express blog](https://expressjs.com/2025/05/16/express-cleanup-legacy-packages.html)). 게다가 EJS/Pug/Handlebars/`res.send` 중 무엇을 고르느냐에 따라 이스케이프 의미가 달라져서 정적 분석 표면과 오탐 위험이 함께 커진다.

실측 데이터도 같은 방향을 가리킨다. BaxBench에서 CWE-79(XSS)는 프레임워크 간 편차가 가장 큰 웹 취약점이었고(.38–1.00), 보안 지시를 줄 때의 하락 폭이 변별력을 직접 보여준다 ([BaxBench v3 Tables 9–11](https://arxiv.org/html/2502.11844v3)).

| 프레임워크 | XSS 없음 → 일반 리마인더 → CWE 특정 지시 | 경로 탐색(없음 → 특정) | 해석 |
|---|---|---|---|
| Flask | **.99 → .90 → .44** | **.33 → .03** | 기본은 거의 전부 취약, 지시에 크게 반응해 변별력 최상 |
| Django | .96 → .80 → .43 | .38 → .09 | 반응은 크지만 CSRF·ORM·해시는 상수화 |
| Express | .95 → .76 → .48 | .30 → .03 | 반응 큼, 템플릿 엔진 분산이 문제 |
| FastAPI | .64 → .60 → .35 | .32 → .08 | 기본값이 이미 낮아 폭이 좁음 |
| NestJS | .93 → .88 → **.86** | .41 → .16 | 프롬프트가 거의 안 먹힘 |
| Rails | .44 → .29 → .10 | — | 기본값이 결과를 결정 |
| Lumen | .38 → .26 → .21 | — | 기본값이 결과를 결정 |

같은 표에서 **SQLi(CWE-89)는 모든 프레임워크에서 .00–.11**로 거의 0이고, 로그 인젝션(CWE-117)은 지시가 없으면 .98–1.00으로 전부 취약이다. 둘 다 프레임워크에 따른 차이가 없다. 비밀번호 저장(CWE-522)은 Flask에서 .28 → .28로 프롬프트에 반응하지 않았다 ([BaxBench v3](https://arxiv.org/html/2502.11844v3)). 실전 에이전트 결과도 이 그림을 뒷받침한다. Cursor, Claude Code, Codex, Replit, Devin이 각각 같은 앱 3개를 만든 Tenzai 실험(총 15개 앱)에서 **악용 가능한 SQLi·XSS는 0건**이었다. 반면 **다섯 에이전트 모두 SSRF를 만들었고**, API 권한 결함이 가장 흔했다 ([SecurityWeek](https://www.securityweek.com/vibe-coding-tested-ai-agents-nail-sqli-but-fail-miserably-on-security-controls/)). 같은 앱을 기본 프롬프트와 보안 요구사항을 덧붙인 프롬프트로 만든 twin-prompt 연구에서는 확인된 취약점이 **51건 → 24건**으로 줄고 Critical/High는 0건이 되었다 ([Andročec, arXiv 2608.20963](https://arxiv.org/abs/2608.20963)). 이는 "프롬프트가 보안 점수를 움직인다"는 부스의 전제를 직접 지지한다. 다만 표본이 앱당 1개라 기술 통계로만 봐야 한다.

여기서 두 가지 함의가 나온다. 첫째, 변별력을 만드는 축은 XSS(템플릿을 우회하는 경로), SSRF, 객체·관리자 권한, CSRF, 세션 비밀키, 업로드다. 그러니 가중치도 그쪽에 실어야 하고, SQLi는 정상 동작 확인용 체크로 비중을 낮춰야 한다. 둘째, 리더보드에서 GPT-5는 "정답 중 취약한 비율"이 약 23%로 상위 모델 중 가장 낮았다 ([baxbench.com leaderboard](https://baxbench.com/static/data/leaderboard_data_none.json)). Codex 계열이 기본적으로 더 안전하게 짤수록 참가자 간 격차는 줄어든다. 이 압축을 상쇄하려면 기본값이 비어 있는 프레임워크에 더해 권한·업로드·세션처럼 기본값으로 해결되지 않는 깊은 프로브가 필요하다. 엔드포인트 수가 늘수록 보안이 나빠진다는 점은 이 부스에 유리하다. AutoBaxBench Hard(엔드포인트 5개)에서 GPT-5는 pass@1 59.3%, sec_pass@1 30.7%로 정답의 **약 55%가 공격 가능**했다 ([AutoBaxBuilder leaderboard](https://baxbench.com/autobaxbuilder)). 엔드포인트가 10개 안팎인 게시판에는 프롬프트가 차이를 낼 여지가 충분하다.

## 정확도는 Python + 서버 렌더링 + stdlib sqlite3 조합에서 가장 높다

탐지 정확도를 결정하는 요인은 언어보다 *구조와 관측 경로*다. SAST는 어느 언어에서나 정밀도는 중상이고 재현율은 낮다. Python 실세계 CVE 108건 벤치마크에서 기성 도구 중 최고는 **Semgrep(정밀도 65.7 / 재현율 40.7 / F1 50.3)** 이었고, CodeQL은 72.3/31.8/44.2, Bandit은 60.0/27.8/38.0이었다 ([PyFlow, arXiv 2608.07026](https://arxiv.org/html/2608.07026v1)). Java 실세계 취약점은 **12.7%만 탐지**되었다 ([Li et al., FSE 2023](https://ink.library.smu.edu.sg/sis_research/8976)). 언어별로 정밀도가 뚜렷이 우월하다는 실측은 없다. 차이는 커버리지 깊이에 있다. Semgrep Pro 규칙 수는 Python이 710개 이상으로 가장 많고, Ruby/PHP는 파일 간 데이터플로를 지원하지 않는다 ([Semgrep supported languages](https://docs.semgrep.dev/supported-languages)). CodeQL은 PHP를 아예 지원하지 않고 Next.js도 모델링하지 않는다 ([CodeQL frameworks](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)). BaxBench에서도 Snyk Code는 익스플로잇이 잡은 취약 프로그램 **64개를 놓쳤고**, 오탐은 **6.75%** 였다. 저자들은 SAST가 벤치마크용으로 부적합하다고 결론 내렸다 ([BaxBench v3](https://arxiv.org/html/2502.11844v3)). 정적 분석은 보조 신호로만 쓰고, 점수가 걸린 판정은 결과로 확인된 동적 증거에 맡겨야 한다는 뜻이다.

동적 쪽에서는 세 가지가 Flask/Python 쪽으로 기운다. 첫째는 **런타임 싱크 관측**이다. Python stdlib의 `sqlite3.Connection.set_trace_callback`은 SQLite 백엔드가 "실제로 실행한 모든 SQL 문"을 콜백으로 넘겨준다 ([Python sqlite3 docs](https://docs.python.org/3/library/sqlite3.html)). 샌드박스에 이미 있는 `sitecustomize.py`에서 `sqlite3.connect`를 감싸면, 고유 canary가 바인딩 파라미터가 아니라 SQL 텍스트 안에 나타나는지로 SQLi를 확정할 수 있다. 에러를 삼켜서 sqlmap이 미탐하는 엔드포인트도 잡힌다. 상용 IAST조차 Python·Node에서는 XSS를 지원하지 않는다 ([Datadog IAST](https://docs.datadoghq.com/security/code_security/iast/)). Node는 sqlite3/better-sqlite3/Prisma/Knex로 드라이버가 갈리고, Go는 런타임 몽키패치가 불가능하다. 둘째는 **의존성 결정성**이다. 레포는 이미 샌드박스 안에서 `pip freeze`로 실제 설치된 버전을 다시 계산한다. Flask 앱의 전이 의존성 트리는 작고 잘 관리된다. npm은 전이 트리가 커서 개발 전용이거나 도달 불가능한 CVE 잡음이 많다는 비판이 오래되었다 ([The Register](https://www.theregister.com/2021/07/09/npm_audit_security/)). 참가자가 고르지 않은 패키지 때문에 점수가 흔들리는 셈이다. 셋째는 **관측면**이다. Jinja·Django 템플릿·ERB·Blade처럼 서버가 HTML을 렌더링하는 스택에서는 반사된 XSS가 HTTP 응답 본문에 그대로 나타나 프로브가 결정적이다. SPA·JSON API 스택(Next.js 클라이언트 컴포넌트, FastAPI + React, NestJS API)에서는 XSS가 DOM으로 옮겨가 헤드리스 브라우저가 필요해진다 ([ZAP SPA 가이드](https://www.cyberly.org/en/how-do-you-use-owasp-zap-to-test-the-security-of-a-single-page-application-spa/index.html)). Next.js Server Actions는 Origin 헤더가 *없는* 요청을 경고만 남기고 통과시킨다 ([Next.js serverActions](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions)). 미들웨어에서만 인증하는 구조는 CVE-2025-29927처럼 통째로 우회될 수 있다 ([Snyk](https://snyk.io/blog/cve-2025-29927-authorization-bypass-in-next-js-middleware/)). 이런 동작을 범용 프로브로 판정하기는 어렵다.

FastAPI를 옹호하는 논리도 공정하게 짚어 보자. 단일 파일에 인기 언어이고, Pydantic 응답 모델이 필드명을 선언적으로 고정하며, `/openapi.json`이 자동으로 생성되므로 oasdiff로 사전 검사를 싸게 할 수 있다. BaxBench에서도 OpenAPI 명세를 주면 pass@1이 6.8–9.3%p 올랐다 ([BaxBench v3 Table 3](https://arxiv.org/html/2502.11844v3)). 하지만 이 이점은 모두 *계약 적합성*에 관한 것이고, 계약 루프는 바로 그 적합성을 어느 프레임워크에서든 보장한다. 앱이 스스로 내보내는 OpenAPI는 선언과 실제 서빙이 다를 수 있으므로 게이트로 쓸 수도 없다. 오히려 비용이 따른다. Starlette 쿠키가 기본 Lax라서 레포의 `csrf_protection`을 그대로 옮기면 FastAPI 앱은 기본값만으로 CSRF 점수를 받는다 ([A01:37-42](../scoring/checks/A01_broken_access_control.py)). Werkzeug 콘솔이 없으니 `debug_true`의 "RCE" 근거도 사라진다. 기본 XSS율이 .64로 이미 낮아 지시에 따른 변화 폭도 Flask보다 좁다. 이 비교에서 FastAPI가 내놓는 것은 루프 반복 횟수가 약간 줄어든다는 정도이고, 잃는 것은 레버와 critical 체크다.

## 종합 추천: Flask 1순위, FastAPI는 조건부 대안, 기본값이 두꺼운 프레임워크는 비추천

| 순위 | 프레임워크 | 변별력 | 탐지 정확도·채점 편의 | 이식 비용 | 판단 |
|---|---|---|---|---|---|
| **1순위** | **Flask (유지)** | 최상. CSRF·SameSite·비밀키·디버그·SQL 방식·업로드·rate limit·SSRF·권한이 모두 레버이고, XSS 지시 민감도도 최상 | Werkzeug 콘솔이 결정적 critical, stdlib sqlite3로 IAST 가능, 의존성 트리 최소, 기존 정적 검사·PoC 그대로 유효 | **S** | 계약 루프와 동적 전환에 투자 |
| 대안 | FastAPI + Jinja2 + 쿠키 세션 | 상. Lax 기본값 때문에 CSRF 레버가 약해지고, 기본 XSS율이 낮아 변화 폭이 좁음 | OpenAPI 사전 검사 가능, Python 도구 체인 유지. 다만 `debug_true` 강등과 세션 위조 서명기(TimestampSigner) 교체가 필요 | **S–M** | 루프 반복 횟수 실측에서 Flask가 크게 뒤질 때만 |
| 조건부 | Express | 레버 수는 최다 | 템플릿 엔진 분산, npm CVE 잡음, `NODE_ENV`를 grader가 정해야 하는 문제, 세션 라이브러리 분산 | M–L | 얻는 것 대비 비용 과다 |
| 조건부 | Go (net/http, Gin) | 중. `html/template`가 XSS를 상수화하고 디버그 레버가 없음 | govulncheck로 의존성 오탐은 최저지만 런타임 계측이 불가 | M–L | 이점 부족 |
| 비추천 | Django | 낮음. CSRF·ORM·해시·헤더가 상수 | 멀티파일 구조, `csrf.py`가 보내는 이름과 충돌, DB 세션이라 위조 판정이 대부분 불가 | M | 루브릭 보정 붕괴 |
| 비추천 | Rails, Laravel, Spring Boot | 낮음 | 빌드·부팅이 무겁고, Laravel `APP_KEY` 필수가 무설정 부팅 규칙과 충돌 | L | 변별력과 운영 모두 불리 |
| 비추천 | Next.js, NestJS | 낮음~중간. NestJS는 XSS 지시에 거의 반응하지 않음 | DOM XSS, 해시된 액션 ID, 빌드가 45초/512MB 안에 끝날지 의문 | L | 관측성 최악 |
| 비추천 | plain PHP | 과도. 업로드 하나로 샌드박스 RCE 가능 | 정적 도구가 가장 약함(CodeQL 미지원) | L | 하한선이 너무 낮음 |

이식 비용 등급은 레포 분석에 근거한다 ([config/scoring.yaml:113-128](../config/scoring.yaml)의 45초 부팅·512MB·1 CPU 제약 포함). Laravel 쪽 충돌은 무설정 부팅 규칙 ([config/default_prompt.md:21-28](../config/default_prompt.md))과의 충돌을 말한다. 다만 이 순위에는 측정되지 않은 부분이 있다. BaxBench는 단발 생성에 구형 모델(o1, GPT-4o 등)이 중심이고, **Codex CLI나 GPT-5 계열의 프레임워크별 결과는 공개된 것이 없다**. 확정하려면 소규모 파일럿이 필요하다. 예를 들어 Flask와 FastAPI 각각에 대해 Codex 생성 10회 × 프롬프트 3종(무지시·일반·구체)을 돌려 점수 분산과 루프 반복 수를 비교하면 된다.

## 계약 루프는 기능만 가르치고 보안은 건드리지 않아야 한다

계약 루프의 정당성은 실측에서 나온다. GPT-5는 보안 지시를 받으면 pass@1이 **70.7% → 57.9% → 50.5%** 로 최대 20%p 떨어졌다 ([baxbench.com specific](https://baxbench.com/static/data/leaderboard_data_specific.json)). 루프가 없으면 보안을 꼼꼼히 쓴 참가자가 기능 실패로 벌을 받는다. 루프는 이 두 효과를 분리한다. 기능 실패 신호만 주는 에이전트 루프가 보안을 바꾸지 않는다는 근거도 있다. OpenHands 에이전트는 기본 프롬프트에서 pass@1을 53.6% → 59.5%로 올렸지만 sec_pass@1은 32.9% → 31.8%로 그대로였다 ([BaxBench v3 Table 2](https://arxiv.org/html/2502.11844v3)). 루프는 정확성을 고치고 보안은 프롬프트가 정하는, 부스가 원하는 분업이다. 이 분업이 깨지는 경로는 세 가지이고, 각각에 설계 규칙이 필요하다.

**보안 중립성.** 계약 테스트는 "소유자·관리자의 정상 경로"만 검사한다. 다른 사용자의 403, 비관리자 거부, 잘못된 입력의 400, HTML 이스케이프는 절대 테스트하지 않는다. 테스트하는 순간 루프가 보안 과외 선생이 되어 참가자의 레버를 지운다. 레포의 계약 문서도 이미 "보안 방어 자체는 언급하지 않는다"는 원칙을 갖고 있다 ([docs/APP_CONTRACT.md:182](../docs/APP_CONTRACT.md)). 이 원칙을 기계적으로 보장하려면 모든 계약 단언을 **취약 샘플 앱과 보안 샘플 앱 양쪽에서 통과**하도록 CI로 검증한다. 레포의 `samples/vulnerable_board`와 `samples/secure_board`가 그 기준이 된다. AutoBaxBuilder가 익스플로잇을 "취약 해법에서 성공하고 패치 해법에서 실패할 때만" 채택하는 대조 규칙을 계약 테스트에 거꾸로 적용하는 셈이다 ([AutoBaxBuilder](https://arxiv.org/html/2512.21132)). 기능 테스트 데이터에는 `<`, `>`, 따옴표, `&`가 없는 무작위 마커만 쓴다. 그래야 결과가 이스케이프 여부에 좌우되지 않는다. CSRF 토큰은 앱이 주면 따르고 없으면 그냥 진행하는 "follow-if-present" 모드로 다루며, 레포의 공용 [scoring/shared/csrf.py](../scoring/shared/csrf.py)를 재사용할 수 있다. Schemathesis를 보조로 쓸 경우 기본 체크에 `ignored_auth`, `object_level_authorization`, `negative_data_rejection`, `use_after_free`, `unsupported_method` 같은 보안 성격의 체크가 켜져 있으므로 형태 검사만 남기고 이들을 명시적으로 꺼야 한다 ([Schemathesis checks](https://schemathesis.readthedocs.io/en/stable/reference/checks/)). 계약은 JSON과 HTML을 함께 정의한다. JSON 엔드포인트는 키·상태코드를 정확히 단언하고, `/posts`, `/posts/<id>`, `/search`, `/users/<id>`는 `text/html`, 지정된 `<form>`의 `name=` 속성, 게시한 마커의 등장 여부만 확인한다. 인증은 쿠키 세션으로 강제한다. JSON 전용에 bearer 토큰이면 CSRF와 XSS 프로브가 공허해진다.

덧붙일 미묘한 점이 있다. 수리 프롬프트에 "인증·CSRF·이스케이프를 바꾸지 마라"처럼 보안 용어를 나열하면, 그것 자체가 보안 리마인더로 작용할 수 있다. BaxBench에서 추론 모델은 일반적인 보안 리마인더만으로도 보안이 상당히 개선되었다 ([BaxBench v3 §4](https://arxiv.org/html/2502.11844v3)). 이는 근거에서 끌어낸 추론이지 측정된 사실은 아니다. 그래도 수리 프롬프트는 "아래 실패 항목만, 필요한 최소 범위로 수정하라. 테스트 하네스를 탐지하거나 특수 처리하지 마라"처럼 보안 어휘가 없는 문구로 쓰는 편이 안전하다. 그리고 수리 전후 스냅샷의 보안 관련 패턴(`login_required`, CSRF 설정, `escape`, 파라미터화 쿼리, 쿠키 플래그)을 비교해, 수리 라운드가 보안 상태를 바꿨으면 "하네스 유발 변경" 플래그를 남긴다. 반복 수정이 보안을 악화시킨다는 연구도 있다. "개선" 반복 다섯 번 만에 critical 취약점이 37.6% 늘었다는 보고가 있다 ([arXiv 2506.11022](https://arxiv.org/abs/2506.11022v2)). 반대로 보안을 *개선*하는 쪽으로 흐를 수도 있으므로, 양방향을 모두 감시해야 한다.

**Reward hacking 방지.** Codex가 쓰는 GPT-5 계열은 테스트가 보이고 수정 가능할 때 높은 비율로 속인다. ImpossibleBench에서 GPT-5는 사양과 충돌하는 테스트에서 **Oneoff-SWEbench 76%, Conflicting-SWEbench 54%** 를 속였다. OpenAI 모델은 테스트 수정, 연산자 오버로딩, 상태 기록, 입력 특수 처리의 네 가지 전략을 모두 썼다 ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)). 같은 연구는 완화책의 효과도 측정했다. **테스트를 숨기면 부정행위가 거의 0**이 되었고, 가장 엄격한 프롬프트는 85% 이상을 1%로 낮췄으며, "포기 선택지"는 GPT-5를 54%에서 9%로 줄였다. 이 결과를 하네스 설계로 옮기면 다음과 같다. 전체 계약 스위트는 Codex 작업공간이 아니라 채점 샌드박스에만 둔다. 실행 단위마다 사용자명, 제목, 검색 토큰, 정렬용 타임스탬프를 무작위로 바꿔 하드코딩을 무력화한다. 수리 프롬프트에 되돌려주지 않는 held-out 부분집합을 남겨, 보고된 항목은 통과하고 held-out만 실패하면 과적합으로 표시한다. "충족할 수 없으면 최종 메시지에 그렇게 밝혀라"는 탈출구를 둔다. 생성 코드는 하네스 지문(테스트 사용자명, grader User-Agent, `if "test" in`)을 정적 스캔한다. 실패 메시지는 요구사항 ID, 요청(메서드·경로·본문), 기대값, 실제값(상태·본문 발췌), curl 재현 명령을 한 줄씩 담고 테스트 소스는 절대 포함하지 않는다. 계약 테스트는 보안 프로브와 같은 컨테이너 이미지와 부팅 경로에서 돌린다. 레포의 생성 호스트는 danger-full-access와 uv venv로 돌기 때문에, 생성 호스트에서는 통과하고 샌드박스에서는 실패하는 드리프트를 이렇게 막는다.

**반복 횟수.** 외부 실행 피드백이 있으면 수리는 효과가 있다. Self-Debugging은 단위 테스트가 있는 과제에서 최대 12% 개선을 보였다 ([arXiv 2304.05128](https://arxiv.org/abs/2304.05128v2)). 하지만 수리 비용까지 계산하면 이득이 "종종 미미하다"는 반론도 있다 ([Olausson et al., ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/9ddc141bdbf9d1db510cefff56c586ad-Abstract-Conference.html)). 피드백과 함께 여러 번 제출하게 하면 통과율은 80% → 83%로 조금 오르지만 부정행위는 33% → 38%로 늘었다 ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)). 따라서 **최초 빌드 후 수리 2라운드(최대 3)** 를 상한으로 두고, 그래도 실패하면 루프를 계속하지 말고 기능 게이트를 실패로 기록하는 것이 맞다. Codex 쪽 구현은 `codex exec --json`의 `thread.started` 이벤트에서 `thread_id`를 잡아 `codex exec resume <id>`로 이어가는 방식이다. resume은 대화 맥락만 유지하므로 샌드박스 플래그는 매번 다시 넘겨야 하고, 이어갈 세션에는 `--ephemeral`을 쓰면 안 된다 ([Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode.md)). 레포는 생성을 최대 5개 병렬로 돌리므로 `--last`는 다른 제출의 세션을 집을 수 있어 금지한다. 현재 생성 상한 600초 ([config/scoring.yaml:111](../config/scoring.yaml)) 안에 수리 라운드를 포함할지, 라운드별 예산을 따로 줄지도 정해야 한다. 라운드별 소요 시간과 통과까지 걸린 라운드 수는 공개된 데이터가 없으니, JSONL `turn.completed`의 사용량 필드를 로깅해 직접 측정해야 한다.

비결정성도 계약에서 미리 정리한다. 정렬은 동점 처리 규칙까지 고정하고(`sort=new`면 `created_at desc, id desc`), 프로브가 의존하는 상태코드는 정확히 고정하며, 그렇지 않은 곳은 2xx를 허용한다. 레포의 rate-limit 판정은 지금 429/423 외에 "too many", "잠금" 같은 키워드에도 기대고 있다 ([scoring/checks/A06_insecure_design.py:13](../scoring/checks/A06_insecure_design.py)). 계약에 "제한한다면 429로 응답한다"는 *신호 규약*만 명시하고 제한 자체는 요구하지 않으면 이 키워드 목록이 사라진다. 이 규약은 루프에서 테스트하지 않고 프롬프트에만 적는다.

## 이 레포에서는 이식보다 휴리스틱 제거가 먼저다

Flask를 유지하면 이식 비용은 **S**다. 계약 스위트 약 300–600 LOC와 프롬프트 수정이면 된다. FastAPI로 옮기면 S–M이 된다. 정적 정규식 약 540 LOC 중 30–40%만 그대로 쓸 수 있고, Flask 마커(`flask_wtf`, `SESSION_COOKIE_*`, `after_request`/Talisman, `render_template_string`)를 Starlette 대응물로 바꾸는 데 150–250 LOC가 든다. 세션 위조 서명기는 `TimestampSigner`로 교체해야 하고 `debug_true`도 강등해야 한다. 그 밖의 언어로 옮기면 정적 검사, 의존성·타이포스쿼팅 소스, 에러 시그니처, 샌드박스, 샘플 픽스처, 프롬프트를 모두 다시 써야 한다. 특히 **Python 전용 정규식에 걸린 critical 감점 41점**(`debug_true` −20, `weak_default_secret` −15, `csrf_protection` −6)이 다시 쓰기 전까지 조용히 사라져 채점이 체계적으로 미탐 쪽으로 기운다 ([scoring/engine/aggregate.py:66-81](../scoring/engine/aggregate.py)). Django라면 grader가 보내는 CSRF 필드·헤더 이름(`csrf_token`/`X-CSRF-Token`, [scoring/shared/csrf.py:22-23, 80-81](../scoring/shared/csrf.py))이 맞지 않아, CSRF로 보호된 앱이 모든 POST에서 403을 받고 기능 게이트부터 떨어질 위험도 있다. 이 부분은 이번 조사에서 직접 확인하지 못했다.

Flask에 남는다는 전제에서 우선순위는 아래와 같다. 앞의 항목일수록 오탐/미탐 감소 효과가 크고 비용이 작다.

## Conclusion

이번 분석의 핵심은 계약 루프가 프레임워크 선택 문제의 성격을 바꾼다는 것이다. 루프가 없을 때는 "어느 프레임워크가 계약을 잘 지키는가"가 큰 변수였고, 그 기준으로는 FastAPI가 유리했다. 루프가 적합성을 상품화하면 남는 기준은 "기본값이 결과를 정하는가, 프롬프트가 정하는가"와 "그 결과를 런타임에서 결정적으로 볼 수 있는가"다. 이 기준에서 보안 기본값이 두꺼운 프레임워크는 안전한 대신 채점기로서는 결과가 미리 정해진 시험지가 되고, Flask의 "비어 있음"은 약점이 아니라 측정 장치가 된다. 같은 이유로 오탐/미탐을 줄이는 지렛대는 프레임워크가 아니라 계약에 있다. 휴리스틱으로 추측하던 신호를 계약의 관측 가능한 마커로 옮기고, 정적 존재 검사를 결과 확인형 동적 증거로 바꾸는 것이 정확도를 가장 크게 올리는 길이다.

남은 위험은 루프 자체가 보안 결과를 오염시키는 것이다. 테스트가 보이면 GPT-5 계열은 높은 비율로 속이고, 보안 용어가 섞인 수리 프롬프트는 의도치 않은 보안 리마인더가 될 수 있으며, 반복 수정은 보안을 어느 쪽으로든 흔든다. 그래서 루프는 짧게(수리 2–3회), 숨겨서, 보안 어휘 없이 돌리고, 계약 단언은 취약·보안 샘플 양쪽에서 통과하는지 CI로 지켜야 한다. 마지막으로 Codex 계열이 점점 더 안전한 기본 코드를 쓰면서 참가자 간 격차는 줄어들 것이다. 변별력은 결국 SSRF·객체 권한·업로드·세션처럼 프레임워크 기본값으로 해결되지 않는 깊은 프로브에서 나오고, 이 프로브들은 계약 루프가 응답 형태를 고정해 줄 때 비로소 결정적으로 돌릴 수 있다.
